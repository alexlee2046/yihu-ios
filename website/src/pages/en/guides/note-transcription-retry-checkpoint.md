<h2 id="first-answer">retry queues preserved fields; it does not automatically clear and re-recognize everything</h2>

Note retry sets the supplied note pending, clears failure and saves without clearing transcript/transcribedFrames there. Transcription opens audio at the recorded frame position and joins later results. Loading leftover recording/transcribing can also mark pending. State reset proves neither complete recovery nor word accuracy, and does not start a new recording.

## Different from recapture, mapping and joining

Recapture assesses missing capture, mapping relates material, joining checks boundaries. Here **what retry retains and where processing resumes** matters. No actual retry, frame edit, model run or restore occurs.

## Synthetic checkpoint note

A failed sample has old text A and position N. Retry queues pending; later work resumes at recorded N. Do not call A new output or pending successful recovery.

Audio, latest persistence and supplied object still need correspondence evidence. Do not edit transcribedFrames to hide gaps. New capture needs a new version; reservations/uncertainty survive retry.

## FAQ

<h3 id="faq-1">Does retry always start at zero?</h3>

This method clears neither text nor position; processing resumes from recorded frames.

<h3 id="faq-2">Does pending prove recovery?</h3>

No. It is queued state, not actual file/model/access acceptance.

<h3 id="faq-3">Is old text all new output?</h3>

No. Separate existing transcript from later pieces.

<h3 id="faq-4">Does advancing an empty piece prove no business speech?</h3>

Not independently. Original audio/meaning need review.

<h3 id="faq-5">Does retry clear handoff reservations?</h3>

Not through this method; it grants no resend authority.

<h3 id="faq-6">Was retry/inference performed?</h3>

No. Source review only, without lossless restore/cloud resume/new capture services.
